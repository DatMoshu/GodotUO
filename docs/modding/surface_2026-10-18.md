# Modding surface audit (2026-10-18)

What someone extending GUO can change today without forking the client, and
what still needs a fork. Measured against `main` at 96ce0ff2 by reading the
code; nothing here was run on a device. Story MOD-01; the follow-ups are
MOD-02 (packet extension points), MOD-03 (`mod` Store pack kind) and MOD-04
(the wiki page).

The case that prompted it: a shard owner on POL modified ClassicUO's packet
handling so the client understands the shard's custom packets, and wants the
same mod in GUO. ServUO and RunUO forks with custom packets are in the same
position. In ClassicUO that mod is always a fork: it edits
`Network/PacketHandlers.cs` (a handler for the new id) and usually
`Network/PacketsTable.cs` (the new id's length), and sometimes adds a gump.

## Summary

| Surface | What it can change | Platforms | Fork needed? |
|---|---|---|---|
| ClassicUO plugin ABI (assistants: Razor, Razor Enhanced, ClassicAssist, native DLLs) | See, edit, drop and inject framed packets both ways; hotkeys, mouse, player position, connect/disconnect, focus, tick; read cliloc, tiledata, static art and file paths; cast a spell, request a step, set the window title | Windows desktop (managed host Windows only) | No |
| Embedded scripts (Razor CE subset, per character) | Run the commands in `docs/embedded-scripting.md`: messages, speech, double-click, cast, target, waits, variables, lists, timers | Every build; mobile and web not verified | No |
| Script components in Store packs | The same runtime, with declared capability grants and an explicit review, approve, enable, run lifecycle | Every build | No |
| Content packs (Store v2 components) | Art (static, land, texmap, gump), hues, sounds, music, animation, wearables, tiledata, lights, fonts, maps, multis, translations; server regions, decoration, loot, spawners, creatures | Every build | No |
| Client-side packs and presets | Themes, splats, HD art, PostFX presets, voices | Every build | No |
| Server-side content | Generic gumps (0xB0, 0xDD), clilocs, items, regions: whatever the shard sends with existing packets | Every build | No (server change, not client) |
| Automation MCP (`tools/guo_mcp`) | Read the UI tree and state, send input, screenshot, overlay captions. No packet, file or script tools | Desktop debug builds, opt-in by environment | No |
| New packet ids, or new lengths for existing ids | The length table is fixed per client version | All | **Yes** |
| A handler for a new or existing packet that changes game state | Handlers are an internal 256-slot table filled in a static constructor | All | **Yes** |
| New 0xBF or 0xF0 subcommands | Both are `switch` statements inside one handler | All | **Yes** |
| New client-side gumps or UI driven by a packet | Gumps are compiled classes | All | **Yes** |
| Renderer, shaders, input semantics | Compiled; L1 changes also need an ADR | All | **Yes** |
| Chat commands, profile fields, Options entries | Registered in source (`CommandManager`, `ProfileManager`, Modern Options); Labs registration is source-only too | All | **Yes** |

The gap that matters for the POL case is the middle of the table: a mod
cannot teach the client a new packet without editing `src/Network`.

## The plugin ABI in detail

GUO hosts upstream's plugin ABI unchanged, so assistants built for ClassicUO
load as they are.

- **Loading.** `settings.json`'s `plugins` array, paths under
  `Data/Plugins`. A DLL with a native `Install` export is called directly
  (`Network/Plugin.cs`). A .NET Framework assembly goes through the managed
  host: `Network/PluginClrHost.cs` starts the .NET Framework CLR in the Godot
  process and `tools/plugin_host` (upstream's Bootstrap, ported to a library)
  loads it. The CLR host is started only when a listed plugin exists, and only
  on Windows. `tools/plugin_probe` checks both paths with test plugins.
- **Header.** `PluginHeader` matches `cuoapi`: client version, HWND, the
  `On*` callbacks the plugin fills in, and the client functions it calls.
- **Packets in.** `PacketHandlers.ParsePackets` frames a packet first, from
  the client's own length table, then hands the framed bytes to every plugin
  (`Plugin.ProcessRecvPacket`). A plugin may rewrite the bytes and the
  length, or return false to drop the packet before its handler runs.
  Packets a plugin injects through `Recv` go to a second buffer and are
  parsed without being shown to plugins again.
- **Packets out.** `ProcessSendPacket` gives every plugin each outgoing packet
  to rewrite or drop; `Send` injects one.
- **Queries.** `GetPacketLength` reads the length table; there is no call to
  change it. `GetCliloc`, `GetTileData`, `GetStaticData`, `GetStaticImage`,
  `GetUOFilePath`, `GetPlayerPosition` read client state.
- **Actions.** `CastSpell`, `RequestMove`, `SetTitle`.

Gaps against upstream, all marked `PORT DEVIATION (GUO)` or `PORT GAP`:

| Upstream behaviour | In GUO |
|---|---|
| `SDL_Window` pointer handed to the plugin | Zero; there is no SDL window in a Godot process |
| HWND from SDL | The Godot window handle, which is the same HWND on Windows |
| `OnDrawCmdList`: plugins draw through the graphics device | Accepted and ignored with one warning in the log (`Plugin.HandleCmdList`) |
| `OnWndProc`: raw SDL window events | Never called; Godot does not produce SDL events |

What a plugin cannot do, and why the POL mod is not a plugin:

1. **It cannot frame a packet the client does not know.** Framing happens
   before plugins see anything. If the shard sends id 0xF5 with a length the
   table disagrees with, the stream desynchronises and every following packet
   is misread. There is no `SetPacketLength`.
2. **It cannot change game state directly.** A plugin can drop a packet or
   inject a rewritten one, but it has no access to `World`, gumps or the
   renderer. To show a custom window it has to translate the custom packet
   into a generic gump packet the client already understands.
3. **It runs only on Windows desktop.** The managed host (every real
   assistant) needs .NET Framework, which is Windows only. The native
   `Install` path is attempted on every platform but has only been probed on
   Windows; Android and web builds ship no `Data/Plugins` folder.

## Packet handling in detail

- `PacketHandlers` is `internal sealed`. Its handler table is a fixed
  `OnPacketBufferReader[0x100]`, one handler per id, filled by
  `Handler.Add(id, handler)` in the static constructor. `Add` replaces
  whatever is in the slot.
- Upstream itself uses that call from outside the file: `Game/UltimaLive.cs`
  registers 0x3F and 0x40 when a shard enables UltimaLive. That is the
  pattern a registered-handler API generalises.
- `PacketsTable` is built per `ClientVersion` in `NetClient.Load`; lengths for
  0x0B, 0x16, 0x31, 0xE1, 0xE3, 0xE6–0xEA, 0x08, 0x25, 0xEE, 0xEF, 0xF1, 0xF2,
  0xF3, 0xB9, 0x24, 0x99, 0xBA, 0x00, 0xFA, 0xFB, 0xD5 and 0xFD depend on the
  version. A mod that adds a packet has to say which client versions its
  length applies to; a mod that claims an id the version already uses must be
  refused or explicitly marked as an override.
- `AnalyzePacket` already catches a handler's exception and drops that one
  packet (a GUO deviation), so a broken handler does not end the frame's
  parse loop. A mod handler gets the same protection for free.
- 0xBF (`ExtendedCommand`) and 0xF0 (`KrriosClientSpecial`) dispatch
  subcommands with a `switch`. Shards often put custom messages in 0xBF
  subcommands; a mod API should accept a subcommand registration as well as a
  top-level id. GUO reserves 0xBF subcommand 0x4755 for its own shard
  offer (`guo/shard-offer@1`, STORE-02); no mod may take it.
- `tools/network_tests` runs the parse loop without the engine. It compiles
  `CircularBuffer.cs` and `PacketLengthGuard.cs` from the client, so a
  registry kept engine-free can be tested the same way.

## Other surfaces in detail

- **Embedded scripting** (`src/Game/Scripting`). A parser and scheduler of our
  own for a subset of Razor CE syntax, one script at a time, nothing starts on
  its own. It routes through `GameActions` and `TargetManager`, never around
  the packet path. No packet commands exist, by design.
- **Script components** (`src/Store/ScriptPackSession.cs`). A v2 pack may
  carry a `script` component with `language: razor-ce`, `runtime: guo-razor`,
  a runtime version and capability grants (`client.message`,
  `player.speech`, `player.inventory.use`, `player.target`,
  `player.spell.cast`, `world.read`, `journal.read`). Installing it runs
  nothing; review, approval (per session, bound to the content hash of the
  whole dependency closure), enable and run are separate steps, and a shard's
  content descriptor can forbid script packs (ADR-0026). This is the existing
  precedent MOD-03 should follow for a `mod` component.
- **Content packs** (`docs/asset_pack_ecosystem.md`, ADR-0019). Data only,
  installation is inert, activation is a restart with a lock file. Signed
  catalogue indexes are verified with Ed25519 (`src/Store/Ed25519.cs`); the
  client verifies and never signs.
- **Automation MCP** (`data_formats` section 29). For agents and test runs:
  it drives the UI like a person. It has no packet tools and is not a
  modding API.
- **Labs** (`src/Labs`). A place for experimental features in a Debug build
  with `GuoLabs=true`; never in an export. It is in-tree development, not a
  way for a third party to ship a change.

## What MOD-02 and MOD-03 need to close the gap

1. A registry in `src/Network` where a mod declares, per packet id (or 0xBF
   subcommand), a length for a range of client versions and a handler, and
   says whether it adds a new id or overrides an existing one. The client
   refuses an override that was not declared and two mods claiming the same
   id.
2. One seam in `PacketHandlers` and `PacketsTable`, marked
   `PORT DEVIATION (GUO)`, consulted only when the L1 option **Load mods** is
   on. Off means the registry is empty and parsing is upstream's, byte for
   byte.
3. Mods are files the user installed. Nothing is loaded from the network, and
   a shard cannot push one.
4. A `mod` Store component that declares the packet ids, subcommands and gumps
   it touches, so the installer can show them before approval and refuse a
   pack whose code registers anything it did not declare.
5. Code in a mod is code: unlike a script component, a managed assembly is
   not sandboxed by capability grants. Review, signing and the user's explicit
   approval are the controls; the ADR for the mod ABI has to say so plainly.
