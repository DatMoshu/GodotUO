# ADR-0007: Android Target

## Status

Proposed — the desktop half is verified; on 2026-09-26 a debug APK built from this tool rendered the login screen on an AYN Thor (see `tools/android/README.md`, the run table). Login and play on the device are not yet verified.

## Date

2026-09-26

## Last Verified

2026-09-26 — on the development machine, which has no Android SDK:
the desktop build is unchanged at 0 errors; `dotnet publish -r android-arm64`
(the .NET half of a Godot Android export) succeeds with no plugin host in the
output; the touch layer passes 18/18 synthetic-finger checks on the desktop
against the dev shard; `launchers\android\doctor.bat` runs and lists what is
missing. No APK has been produced and no phone has run the client. The
verification table in `tools/android/README.md` is the record.

## Decision Makers

Project owner; `uo-render-engineer` (input, render targets);
`uo-port-strategist` (what the port carries to a second platform).

## Summary

GUO gains Android as a second platform, ARM64 only, built from the same Godot
project and the same C# with no second code path in the game: the platform
differences are confined to the csproj (one guarded property), a touch input
layer under `src/Input/Touch/` that turns fingers into the mouse events the
client already consumes, a bootstrap flag, and a build tool under
`tools/android/`. The proprietary UO data lives in the app's own external
files folder on the device, pushed by adb, never packaged. The Windows plugin
host is compiled out on every non-Windows target. The renderer, the window
model and the pixel-art rules are untouched: the client keeps drawing at an
integer scale of its own choosing, and Godot's stretch stays disabled.

## Context — measured, not assumed

### What a Godot 4.7.2 .NET Android export is

Read from the 4.7 export plugin (`platform/android/export/export_plugin.cpp`),
the .NET export plugin (`modules/mono/editor/GodotTools/.../ExportPlugin.cs`)
and `Godot.NET.Sdk`'s `Sdk.props`, and from the 4.7 documentation:

- **.NET on Android is supported** since 4.2 and, in 4.7, still only for
  `arm64` and `x86_64`. There is no 32-bit ARM. The runtime is Mono JIT
  (`dotnet/android_use_linux_bionic` swaps in the linux-bionic runtime; off
  by default and left off here).
- The export runs, by itself,
  `dotnet publish -c ExportDebug -r android-arm64 --self-contained true
  -p:GodotTargetPlatform=android -o <dir>` and packs the output into the
  prebuilt template APK. `Godot.NET.Sdk` derives `GodotTargetPlatform` from the
  RuntimeIdentifier when it is not given (`android-arm64` → `android`; none →
  `windows` on a Windows host) and defines `GODOT_ANDROID;GODOT_MOBILE`.
  `AllowUnsafeBlocks` is unaffected; `EnableDynamicLoading` is not needed;
  memory-mapped files work through Mono's `MemoryMappedFile` on bionic.
- **A plain APK needs no Gradle build and no NDK.** Gradle (`gradle_build/
  use_gradle_build`) is only for an AAB or an Android plugin. The prebuilt
  template compiles against SDK 36 with minSdk 24, so Android 7.0+ is the
  floor.
- The export needs, on the build machine: **JDK 17** (not 21+); the Android
  SDK with `platform-tools`, `build-tools` (35.0.1 in the docs) and a platform
  (`android-35`); the **mono export templates** for exactly 4.7.2 unpacked
  under `%APPDATA%\Godot\export_templates\4.7.2.stable.mono`; a **debug
  keystore**; and a `.sln` next to the csproj (`GUO.sln`, gitignored,
  generated by the editor).
- Godot reads the SDK path, the JDK path and the keystore from
  **`export/android/*` keys in its editor settings file** and nowhere else.
  `ANDROID_HOME` / `JAVA_HOME` are not consulted. A headless export
  (`--headless --export-debug "Android" out.apk`) reads the same file and
  needs a preset named `Android` in `export_presets.cfg`.
- `export_presets.cfg` holds the keystore path and password in clear text and
  is gitignored in this repo. The default debug key (`androiddebugkey` /
  `android`) is the same on every developer machine on earth and is not a
  secret; it is still not committed, on principle and so the file can also
  carry a release key one day.

### Where the client data can live

The client reads its `.mul`/`.uop` files by path, through memory-mapped files
and seeks, from the folder `UO_CLIENT_DATA` (or `--client-data`) names. On
Android the candidates are:

| Where | Permission | adb-writable | Survives uninstall | Notes |
|---|---|---|---|---|
| inside the APK / PCK | none | n/a | n/a | packages proprietary data: forbidden by rule 8; >2 GB anyway |
| app internal storage (`/data/data/<pkg>/files`) | none | debug builds only, via `run-as` | no | invisible to a file manager |
| **app external files** (`/sdcard/Android/data/<pkg>/files`) | **none** | **yes** | no | visible to adb and file managers, removed on uninstall |
| shared storage (`/sdcard/UO`) | `READ_EXTERNAL_STORAGE` (≤ API 32) or `MANAGE_EXTERNAL_STORAGE` | yes | yes | all-files access is a Play policy problem and a runtime prompt |
| Storage Access Framework | user picks a folder | n/a | yes | Godot has no SAF; content:// URIs cannot be mmapped |

### The plugin host

`tools/plugin_host` is a .NET Framework 4.8 project that hosts Razor-style
assemblies; it is a `ProjectReference` from `GUO.csproj` plus two copy targets.
A publish for `android-arm64` fails in it before any GUO code is compiled:

```
error NETSDK1032: The RuntimeIdentifier platform 'android-arm64' and the
PlatformTarget 'x64' must be compatible [tools\plugin_host\GUO.PluginHost.csproj]
```

`PluginClrHost.cs` already guards everything at run time on `OperatingSystem.
IsWindows()`, so nothing in the game needs it at compile time.

### Windows, DPI and scale

The client owns its window size: `GameController` asks `DisplayServer` for
640x480 on the login screen and the profile's size in game. It draws one
client pixel per screen pixel, then `RenderTargets` presents the frame with
`PointClamp` at an integer `DpiScale = ScreenGetScale * ScreenScale`, and
`Mouse.Update` divides window coordinates by the same `DpiScale`. Godot's
stretch is disabled (`project.godot`, see ADR-0001). A phone gives a
2400x1080-class window that the client cannot resize, at 3x density, so a
640x480 login screen drawn 1:1 would be a stamp in a corner.

### Input

`GodotInput.cs` (`src/Input/`) receives every `InputEvent` from
`GameController._Input`, which marks all input handled — so no Godot
`Control` in the tree ever gets an event — and turns mouse and key events
into the SDL-shaped `Mouse`/`Keyboard` state the ported game reads. The game's
own conventions, from `GameSceneInputHandler.cs`:

| Mouse | Game |
|---|---|
| right button held | walk toward the cursor; run beyond 190 px from centre |
| left click | select / target / gump button |
| left double click (≤ `Mouse.MOUSE_DELAY_DOUBLE_CLICK` = 350 ms) | use / open |
| left drag past `MIN_PICKUP_DRAG_DISTANCE_PIXELS` (5) | pick up |
| right click over a gump | close it, if `CanCloseWithRightClick` |
| Ctrl + wheel | zoom, only when `Profile.EnableMousewheelScaleZoom` |

Prior touch UO clients, read for what they chose: **MobileUO** (Unity) adds a
virtual joystick and maps tap to click; **UltimatumUO** keeps tap as click,
makes a long press on the world the held right button, and disables long
press over gumps because a held press there is a pickup. Neither has pinch
zoom; there is no official touch client.

### Audio

`src/Render/Sounds` plays through Godot `AudioStreamPlayer`s (ADR-0005); the
Android audio driver is Godot's business and the client code is
platform-neutral. Nothing to decide.

## Decision

### 1. ARM64 debug APK, no Gradle, preset from a tracked template

One export preset, `Android`, rendered by `tools/android/run.py` from
`tools/android/export_presets.template.cfg` into the gitignored
`godot/GUO/export_presets.cfg`, with the keystore path and password coming
from `launchers/_shared/config.bat` (`UO_ANDROID_*`, `if not defined`
guarded, mirrored in `tools/guo/config.py`). `arm64-v8a` only; Gradle off;
`permissions/internet` the only permission; `dotnet/include_debug_symbols`
on. The tool writes the three `export/android/*` editor settings from the same
config before every export, so the editor never has to be opened to set
them, and runs `godot-console --headless --export-debug`. A release preset
is a later ADR: it needs a real key and a decision about distribution.

The tool has one entry point per job — `doctor`, `templates`, `keystore`,
`settings`, `preset`, `export`, `install`, `run`, `logcat`, `push`, `smoke`
— behind five launchers in `launchers/android/`. `doctor` prints every
missing thing with its exact fix, so the next machine can get to a green
export without reading engine source.

### 2. Client data in the app's external files folder

`UO_ANDROID_CLIENT_DATA` defaults to
`/sdcard/Android/data/<package>/files/uo`; `run.py push` copies
`UO_CLIENT_DATA` there with `adb push --sync`. The path is baked into the APK
through `command_line/extra_args` as `--play --client-data <path>`, which is
how `UO_CLIENT_DATA` resolves on a platform with no launcher and no
`config.bat`: the same flag the desktop `Main.cs` already parses, so nothing
in the resolution order changes — the value merely arrives on the command
line instead of the environment.

Why this folder: no permission, no runtime prompt, no Play policy exposure,
mmap works (it is a real filesystem path), adb and any file manager can write
it, and uninstalling the app removes the proprietary data with it. What it
costs: the data goes away on uninstall (a reinstall keeps it) and a user with
no PC has to copy several GB through a file manager. Neither is worse than
the desktop client, which also needs the install copied by hand.

### 3. The plugin host is a Windows-only build item

`GUO.csproj` defines

```xml
<GuoPluginHost Condition="'$(OS)' == 'Windows_NT' and
  ('$(GodotTargetPlatform)' == '' or '$(GodotTargetPlatform)' == 'windows')">true</GuoPluginHost>
```

and the `ProjectReference` plus the `CopyPluginHost`/`PublishPluginHost`
targets are conditioned on it. A desktop build or Windows export sees exactly
the same project as before; an Android (or Linux, or macOS) publish never
touches `tools/plugin_host`. `PluginClrHost` keeps its run-time
`IsWindows()` guard, so on a device plugins are simply absent, which is the
correct answer for Razor-shaped assemblies built against .NET Framework.

### 4. Window and scale: the client's own integer scale, not Godot's stretch

On a mobile target (or `--touch`) the bootstrap sets
`Client.Game.ScreenScale = max(1, shorterWindowSide / 480)` once the window
exists (`--screen-scale N` overrides it). Everything downstream already
exists: `RenderTargets` presents at that integer factor with `PointClamp`,
`Mouse.Update` divides by it, and the client sees a logical window of
(physical / scale), so a 2400x1080 phone runs the client at 800x360 logical
at 3x — pixel art stays nearest-neighbour and integer (rule 7), and no Godot
viewport is resized or scaled. `window/handheld/orientation` is set to
sensor-landscape in `project.godot`; it is ignored on the desktop.

Not done, and deliberately: no stretch mode (it would scale a fixed-size root
viewport and filter it), no separate mobile project, no DPI-aware layout in
the gumps — they are the original client's gumps at the original client's
pixel sizes, and on a 480-line logical screen that is the honest tradeoff.

### 5. Touch controls: a translation layer, not a new input model

`src/Input/Touch/TouchInput.cs` sits in front of `GodotInput.Handle`. When
enabled (`OS.HasFeature("mobile")`, or `--touch` on the desktop, in which
case `emulate_touch_from_mouse` is also switched on so a mouse can stand in
for a finger) it consumes `InputEventScreenTouch` / `ScreenDrag` /
`MagnifyGesture`, swallows Godot's own mouse events (except the wheel) so
nothing arrives twice, and feeds synthetic `InputEventMouseButton` /
`InputEventMouseMotion` / `InputEventKey` into the unchanged `GodotInput`.
The game never learns a finger exists.

| Gesture | What the game receives | Why this mapping |
|---|---|---|
| tap | left press + release | the universal click; MobileUO and UltimatumUO both do this |
| second tap within 350 ms | left press again → the game's own double-click detection | use/open, at the game's own threshold, not a new one |
| hold ≥ 220 ms on the **world** | right button held until the finger lifts; the finger's position is the cursor, so distance from centre = walk vs run | how the original walks; a joystick would be a new model and would need the pathfinder |
| hold ≥ 220 ms on an item (`ItemGump`, or a paperdoll slot) | left button held → the game's drag past 5 px = pickup, release = drop | a held press over an item must be a pickup, as UltimatumUO found |
| drag on a gump elsewhere | left held → the gump moves | gumps are dragged by the left button |
| hold ≥ 550 ms without moving, not on the world | right click | close-gump / context, where nothing else claims a long press |
| second finger | pinch: every 40 px of change → one Ctrl + wheel step | the game's own zoom path; the profile flag `EnableMousewheelScaleZoom` is forced on, marked `PORT DEVIATION (GUO)` |
| tap on the gump bar | the corresponding `GameActions.Open*` | see below |

Timings: `HoldMs = 220` (below the game's 350 ms double-click window, so a
second tap is never mistaken for a hold), `LongPressMs = 550`, `MovePixels =
12` (a finger jitters more than a mouse; the game's 5 px pickup threshold
still applies after the hold has decided the gesture).

**The gump bar** (`TouchGumpBar.cs`) is a `CanvasLayer` with seven flat
buttons along the bottom right — paperdoll, backpack, journal, map, chat,
options, keyboard — that appear once the world is in and mirror
`TopBarGump`'s actions; keyboard calls `DisplayServer.VirtualKeyboardShow`.
It is an overlay, not a gump, because: it must exist before the profile and
outside the world's render-target path (so it never enters the batcher or
gets scaled/filtered with the frame); it must not be closable, movable or
saved with the gump layout; and it needs no game state beyond "in game". It
draws with `_Draw` rectangles and the fallback font, takes no Godot input
(nothing can — `GameController._Input` handles everything), and is
hit-tested by the touch layer, which is why the layer, not the bar, sends
`bar -> <action>` to the trace. Its size scales with `ScreenScale`.

Not done: a virtual joystick (the held right button already walks and runs);
gesture-to-macro binding (macros are a profile feature and a later step);
edge-swipe gump paging; haptics.

### 6. Out of scope for this ADR

Release signing and distribution; the Play Store; an AAB; Android plugins
(and therefore Gradle builds); iOS, which reuses the touch layer but needs
its own export decisions; a controller mapping; on-device shard discovery;
save-game and profile sync between devices; any change to the gumps' pixel
layout for small screens.

## Alternatives Rejected

- **Godot stretch (`canvas_items`/`viewport`) for the phone.** Filters the
  frame and keeps the root viewport at a size the client did not ask for;
  ADR-0001's reasons all still apply. The client's own integer `ScreenScale`
  path gives the same result without touching the renderer.
- **A virtual joystick.** Every prior touch UO client that added one also had
  to add its own walking model on top of the game's right-button one; the
  held finger *is* the right-button model and needs nothing new.
- **Shared storage with `MANAGE_EXTERNAL_STORAGE`.** Works on a personal
  phone, but is a runtime prompt on every install and a Play Store policy
  violation for an app that does not need all files.
- **Packaging the data in the APK.** Rule 8.
- **A Gradle build.** Needs an NDK and the Android source template, minutes
  per export, and buys nothing until an AAB or a plugin is wanted.
- **`#if GODOT_ANDROID` around the plugin host in C#.** The failure is in
  MSBuild before C# runs; only a project-level guard fixes it. The run-time
  `IsWindows()` guard stays because it is upstream's shape.
- **Making the gump bar a `Gump`.** It would live in the profile's gump
  list, be closable, and be scaled and drawn through the world's render path;
  every one of those is wrong for a control that must always be there.
- **Waiting for the machine to have an SDK before writing any of this.** The
  .NET half, the touch layer and the tool can all be proven on the desktop,
  and were; only the last mile needs the SDK.

## Consequences

- Windows desktop: nothing changes. Same csproj evaluation, same input path
  (`TouchInput.Enabled` is false unless `--touch`/mobile), same window model.
  `dotnet build` stays at 0 errors; the plugin host is still built and copied.
- Every non-Windows target loses plugin support at build time, which matches
  what it had at run time already.
- A new tool folder (`tools/android/`), a new launcher group
  (`launchers/android/`), eight new `UO_ANDROID_*` settings, and a new input
  folder (`src/Input/Touch/`, two files). No upstream file changed shape; the
  hooks in `GameController.cs` and `Main.cs` are marked `PORT DEVIATION (GUO)`.
- The desktop gets `--touch`, `--touch-probe`, `--login-probe`,
  `--login-probe-stay` and `--screen-scale N` as side effects, all opt-in.
- `Profile.EnableMousewheelScaleZoom` is forced on while pinching. It is a
  saved profile setting, so a pinch on a device leaves it on for the desktop
  profile of the same account if the two share a profile folder. Recorded as
  a deviation; the alternative (a private zoom path) would duplicate
  `Camera` logic.
- The doctor is the contract for the next machine. When the SDK versions in
  the Godot docs move, `tools/android/run.py` and this ADR's context section
  move with them; the pinned engine (4.7.2) does not.
